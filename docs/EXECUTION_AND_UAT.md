## 1. 这次解决的核心问题

一次同步有四种不同事实：数据能否完整编码、请求是否被接受、目标是否已经显示预期值、用户最终拿到的程序是否就是被测试的文件。不能用一个布尔 `success` 混淆它们。

```text
读取配置和源数据
       |
       v
读目标快照 -> 计算所有 action -> 全量转换和后端编码检查
                                      |
                         任意值不合法 +--> 零写入，返回位置/字段
                                      |
                                      v
                            按 action 顺序执行写入
                                      |
                   +------------------+--------------------+
                   |                  |                    |
               明确失败           结果未知              已接受
                   |                  |                    |
                停止后续         不自动重放写入        读取预期结果
                                                           |
                                                暂时旧值 -> 等待后只读
                                                           |
                                             已确认 / 超时未确认 / 读错误
                                                           |
                                        后续 action 的依赖状态就绪才继续
                                                           |
                                        分单位输出接受数与实际确认数
```

这是顺序执行器加一个小型只读等待模块，没有引入任务队列、数据库、后台线程或新运行依赖。远端 API 自身明确允许的失败重试规则保留；**读回失败不会触发写入重放**。

## 2. 全量预检查，而不是边写边发现本地错误

`SyncService` 在规划完成后，检查所有待写记录；执行前再检查实际进程内计划。实际 v1/v3 编码器同时被预检查和发送路径调用，避免维护两套不同规则。检查包括可写字段、值类型、日期/数字、JSON 有限数、重复或缺失的更新/删除 ID，以及 Sheet 范围和矩阵形状。

这保证已知的本地数据错误不会在前几个批次写完后才出现。它不保证远端状态永不变化，也不能提前证明服务端一定接受某个新字段。创建缺失字段后，必须等实际 schema 可见，再与计划类型核对并重新检查记录；此时失败，已创建的字段会明确记录，不假称整个任务零副作用。

非空数值转换失败不再返回空值并忽略。错误信息提供记录位置与字段，用户应修正源数据，而不是重复运行。公开 dry-run 仍不导出完整记录正文或可重放 mutation payload。

## 3. 读回确认：有界、精确、不会越等越多写

配置如下：

```yaml
sync:
  verify_remote_writes: true
  verify_timeout_seconds: 10.0
  verify_interval_seconds: 0.5
```

`verify_remote_writes` 默认仍为 false；这是向后兼容选择，不是推荐把未确认当确认。CLI 同样支持 `--verify-remote-writes --verify-timeout-seconds 10 --verify-interval-seconds 0.5`。

首次读取立即执行。未观察到预期值时逐步退避，初始间隔 0.5 秒；默认退避到 2 秒，显式配置更大初始间隔则不缩短它；尊重有效的 Retry-After。范围为 timeout 0–300 秒、interval 0.05–60 秒；timeout=0 只读一次。两者均拒绝 NaN、Infinity 和布尔值。

**时间边界：**timeout 是一轮确认的后续读取调度窗口，不是整个同步的硬超时，也不会中断正在执行的 HTTP 请求。一次读取有独立的 HTTP 超时/重试预算；多 action 可有多轮确认。不使用“等 10 秒必然结束”这种不成立的承诺。

Base 记录只重读尚未确认的 ID，已确认记录不会每轮全表扫描；ID 批量和字段投影各自分块。删除检查真正缺失，字段创建检查实际 schema。后续 action 依赖的快照也等本次变更可见后再推进；无法解释的变化不自动当成本程序的成功。

永久错误、异常响应和不完整读取立即停止；暂时不可见和明确可重试的读取错误才进入等待。部分记录先成功时按真实 ID 计数，不假设成功的一定是列表前缀。

### 匹配键与写入值是两套语义

| 数据 | 匹配可以怎样做 | 确认写入必须怎样做 |
|---|---|---|
| 日期 | `day` 可按指定时区归入同一业务日 | 比较同一毫秒时间值，不能“同一天就算相等” |
| 文本 | 按索引自己的规范化规则匹配 | 普通文本保留空格，不擅自 trim 后相等 |
| 多选/人员/关联 | 按字段种类处理 | 忽略无意义顺序，但保留重复元素的数量差异 |
| 数字与布尔 | 按索引类型匹配 | 不让 Python 的 `True == 1` 掩盖类型错误 |
| Sheet 空值 | 无索引含义 | 可容忍响应省略末尾空值，不能抹掉中间物理空行 |

普通文件日期的无时区值统一按 UTC，带 offset 按实际瞬间；缺少年份或含糊值拒绝。北京时间建议显式 `+08:00`。索引日粒度必须给出 IANA 时区。百分数保留原约定：`12%` 写成 12，不是 0.12。长编号应使用文本；不能无损表达的数值提前报错。

### Sheet 读回与公式扫描

普通值用 `UnformattedValue` 比较；需要确认显式公式对象时用 `Formula`，清空检查也用 Formula，防止把 `=""` 当成空单元格。读取选项按调用传入，不修改共享客户端的全局选项。

Sheet AI 扫描截断时，先拆范围组，再按行、列二分单个 A1 范围。只累计完整叶子范围，父范围不重复计数。单格仍截断、已发现真实公式错误、返回无效，或达到 **128 次客户端逻辑探测**时停止。128 只是限制本程序工作量，不是声称飞书最多能扫多少单元格，也不是整次任务 HTTP 总数上限。

普通文件字符串 `=...` 不被自动执行为公式；明确的 API 公式对象采用 `{type: "formula", text: "=..."}`。本工具不新增 Excel 公式自动翻译功能。

## 4. 结果应该让用户看懂

JSON 新增 `summary.accepted_by_unit`、`confirmed_by_unit`、`counts_are_operations`、`confirmation_complete`。记录、行、列、范围和字段分别统计。删除后重建是两个操作，不是“一个唯一业务记录”。原状态值和原退出码保留。

| 情况 | 用户应理解的结果 |
|---|---|
| 数据错误，在首个写入前发现 | 没有写入，修正提示的记录/字段 |
| 请求已接受，未启用读回 | 已提交；不等于已读回确认 |
| 已接受，所有对应值读到预期结果 | 已确认对应写入 |
| 部分 ID 已确认，其他等到超时 | 显示接受数、确认数；不把未确认数报成确定失败数 |
| 写请求响应丢失 | 结果未知；先检查目标，不自动重跑 |
| 数据确认成功，但附加格式处理未确认 | 数据与附加操作分别说明，不显示整个任务全部已确认 |

读取等待超时为退出码 7 / `XTF_E_CONFIRMATION_TIMEOUT`。`confirmation_complete` 还要求整体成功，不会因为前面数据确认了就忽略后面的公式失败。字段创建的确认状态从 `pending_schema` 到 `schema_confirmed`，不会发送成功就立即写“已确认”。

## 5. 算法与代价

设待写记录数为 N，字段数为 F，一轮未确认 ID 数为 P，ID 上限为 R、投影上限为 C：

- 本地转换和预编码按待写单元格量线性处理，约 O(N×F)；不额外缓存一份全量编码 JSON。修复了逐单元格复制字段字典导致的多余 O(F) 操作。
- 一轮定点读取约需 `ceil(P/R) × ceil(F/C)` 次接口调用。已确认 ID 从后续轮次移除，避免反复全表读取；多次调用并不构成远端原子快照。
- 索引匹配继续使用既有索引结构，不新增逐源行扫描整张目标表的算法。
- 公式二分的路径长度随范围尺度对数增长，总探测次数另有 128 上限；不是无限递归/不断减半直到服务成功。

没有给出未经基准测量的“速度提高百分比”。启用读回会增加网络成本，这是确认实际结果的必要代价；普通单次成功读取不会额外等待。

## 6. 真实 UAT 的运行方法

脚本已实现并完成离线分支测试，**本次没有执行真实 Feishu 请求**。普通 pytest 不会启动 live 套件。

### 资源和输入

GitHub 环境 `feishu-api-ci` 使用五个 Secret；本地使用同名环境变量：

| 名称 | 用途 |
|---|---|
| `XTF_UAT_APP_ID` / `XTF_UAT_APP_SECRET` | 用于测试的自建应用 |
| `XTF_UAT_BASE` | 专用 Base。Base 两套测试均使用它，每次各建一张唯一名称的临时表 |
| `XTF_UAT_SPREADSHEET` / `XTF_UAT_SHEET_ID` | 专用 Sheet：名称以 `XTF_UAT_` 开头，至少 200 行、20 列，整张工作表必须完全为空 |

不要提供业务表作为 Sheet fixture。Sheet 为预建专用子表，不是脚本猜测创建接口；获取前以 Formula 模式分块检查整个网格，不清空已有内容。样例读写使用 `A1:T200`，但 clone 会清空整张工作表，因此整张工作表必须专用且不允许并行人工编辑。Base 套件删除的仅是本次创建且已知 ID、名称匹配的表，不删除整个 Base。

```bash
# 先在当前终端环境设置对应 XTF_UAT_*，不要把真实 secret 写入此文档。
python -m tools.feishu_uat --suite base_v3 \
  --manifest reports/base-v3-resource.json --report reports/base-v3.json
python -m tools.feishu_uat --suite bitable_v1 \
  --manifest reports/base-v1-resource.json --report reports/base-v1.json
python -m tools.feishu_uat --suite sheet \
  --manifest reports/sheet-resource.json --report reports/sheet.json

# 指定已构建的真实可执行文件，而不是重新编译：
python -m tools.feishu_uat --suite base_v3 --executable /path/to/XTF \
  --manifest reports/binary-resource.json --report reports/binary.json

# 中断后仅清理已知清单记录的那个资源，环境必须仍指向同一目标：
python -m tools.feishu_uat --suite base_v3 --cleanup-only \
  --manifest reports/base-v3-resource.json --report reports/cleanup.json
```

每次执行使用不同 manifest 路径；不要覆盖需要处理的旧清单。缺少配置退出 2 / `not_configured`，不是成功跳过。首个测试失败和清理失败分别保留；清理失败也使整套失败。已知 ID 在创建后立即保存；创建响应丢失、ID 未知时不猜 ID、不重建、不按名称整批删除。`finally` 与 SIGTERM 尽力清理，SIGKILL/宿主机故障不能保证清理，需保留清单恢复；本包没有全局过期资源扫描删除任务。

### 已编写的真实场景

Base v3/v1 各自包含 201 条多类型 round-trip、前导零、原始文本、日期毫秒、多选两个值、false 布尔值；选择性更新保留 ID 与其他字段；新字段创建后写入；增量不改已有行；第 201 条错误时零写入；空源 clone clear-only。

Sheet 包含 B3 起始的乱序表头、空行和物理行更新；追加到第 7 行；普通更新与追加须保留 A1 哨兵，空源 clone 则须同时清空 A1 与数据区；显式正常公式与除零公式，既检查表达式也检查 `=1+1` 实际得到 2。套件合成的同步输入是 CSV；XLSX 中文路径的读取另由离线产物 smoke 覆盖，不声称这里已测试 Excel 全功能导入。

大范围真实截断、所有人员/关联字段、完整工作簿样式和所有接口边界不在当前 live 场景中；相应离线场景不能冒充真实测试。v3 与 Sheet AI 的租户可用性必须通过真实执行确认。
